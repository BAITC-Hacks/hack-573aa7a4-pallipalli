# PalliPalli — агент тарифных кампаний (Beeline, трек 04)

Агент решает, каким абонентам какой тариф предложить и через какой канал, чтобы
выручка (ARPU) выросла сильнее, чем мы потратим на коммуникацию. Сначала он
проверяет гипотезы небольшими пилотами, а потом запускает до 10 кампаний.

Код решения лежит в [agent.py](agent.py), остальные файлы — из пакета
организаторов.

## Идея коротко

Агент действует как осторожный маркетолог:

1. По истории переходов прикидывает, какие смены тарифа выглядят выгодными, но
   не доверяет этой прикидке полностью.
2. Тратит 20 пилотов на гипотезы, проверка которых сильнее всего может изменить
   итоговый план.
3. Запускает только кампании, которые выгодны даже при пессимистичной оценке
   эффекта, и выбирает канал по тому, окупается ли он для этих абонентов.

## Как делим аудиторию

Аудиторию режем на **ячейки**: текущий тариф × ARPU-сегмент (LOW / MID / HIGH),
например «tariff_13, LOW». Ячейки меньше 60 абонентов пропускаем: на них и пилот,
и кампания получаются слишком шумными. В мок-среде остаётся 27 ячеек.

## Шаг 1. Первая оценка по истории

Для каждой ячейки и каждого возможного целевого тарифа смотрим в
`data/change_tariff.csv` на тех, кто раньше сам перешёл с этого тарифа на
целевой: насколько в среднем изменился их ARPU и как часто встречается такой
переход. Произведение этих двух чисел — наша первая оценка эффекта.

К каждой оценке прикладываем погрешность:

- история описывает других людей и добровольные переходы, а не реакцию на
  предложение, поэтому погрешность берём широкую, около ±100% от самой оценки;
- если переходов в группе мало, подтягиваем оценку к среднему по этой паре
  тарифов;
- если такого перехода в истории нет вовсе, оцениваем по разнице цен тарифов и
  даём ещё большую погрешность. Если файла с историей не окажется, агент
  работает только на ценовой прикидке.

Для каждой ячейки оставляем 4 самых перспективных тарифа по оптимистичной оценке
(оценка + погрешность). Это кандидаты на проверку, в мок-среде их 108.

## Шаг 2. Пилоты: проверяем то, что может изменить решение

Пилотов всего 20, все 108 гипотез не проверить. Перед каждым пилотом агент для
каждого кандидата и каждого размера (40, 80, 120 или 200 абонентов) оценивает,
насколько вырастет прибыль итогового плана, если мы узнаем результат, и вычитает
стоимость пилота. Запускается пилот с наибольшей чистой пользой (метод
*knowledge gradient*).

На практике это значит:

- гипотезу, которая уже точно хорошая или точно плохая, повторно не проверяем:
  решение от этого не изменится;
- большие ячейки с дорогими абонентами проверяем охотнее, потому что ошибка там
  стоит больше денег;
- размер пилота подбирается сам: иногда хватает 40 человек, иногда нужно 200;
- если ни один пилот уже не окупается, разведка заканчивается раньше, а контакты
  остаются на кампании.

После пилота старая оценка и результат объединяются с весами по точности: пилот
на 200 абонентах сдвигает оценку сильно, на 40 — слабо. Поэтому одна неудачная
выборка не переворачивает картину.

Ограничения разведки:

- пилоты идут через SMS: контакт стоит 4 у.е., а отдача выше, чем у бесплатного
  push, поэтому эффект в пилоте заметнее;
- на пилоты уходит не больше 25% общего охвата, а один пилот берёт не больше
  половины ячейки, чтобы осталось кого охватить кампанией.

## Шаг 3. План кампаний

1. Для каждой ячейки выбираем лучший тариф по пессимистичной оценке (оценка
   минус одна погрешность). Если она не больше нуля, ячейку не трогаем: мы не
   уверены, что заработаем.
2. Для каждого канала считаем выгоду на контакт: средний ARPU ячейки × эффект ×
   эффективность канала − цена контакта.
3. Раздаём охват (15 000 контактов) самым выгодным ячейкам через дешёвый канал
   (push или SMS, что выгоднее для ячейки), пока не кончатся контакты или деньги.
4. Остаток бюджета тратим на переход на дорогой канал (реклама, звонок) там, где
   доплата окупается лучше всего. Обычно это дорогие абоненты с сильным эффектом.
5. Ячейки с одинаковым целевым тарифом, каналом и сегментом собираем в одну
   кампанию до 5 000 абонентов. Если кампаний больше 10, оставляем 10 самых
   прибыльных.

Если ни одна ячейка не прошла порог, агент возвращает одну бесплатную
push-кампанию на самую перспективную гипотезу. Так решение остаётся корректным и
ничего не стоит.

## Почему такой подход

- **Нет зашитых эффектов.** Всё, что агент знает об эффектах, он берёт из
  истории и пилотов. Каналы, тарифы, остаток бюджета и охвата читаются из `env`,
  поэтому другие эффекты на судействе логику не ломают.
- **Осторожность.** Кампания запускается по пессимистичной оценке, так что один
  случайно удачный пилот не приведёт к дорогой ошибке.
- **Деньги идут туда, где окупаются.** Дорогой канал получают только абоненты,
  у которых прирост ARPU покрывает доплату за контакт.

## Результаты на мок-среде

Один прогон (`seed=42`):

| Метрика | Значение |
|---|---|
| Чистый результат | 4 772 379 (+3.17% к baseline) |
| Затраты | 97 948 из 100 000 у.е. |
| Пилотов | 20 из 20 |
| Кампаний | 6 |
| Контактов | 9 313 из 15 000 |
| Абонентов с отрицательным эффектом | 0% |

Устойчивость (`--runs 10`): медиана 4 778 752, минимум 4 319 999, максимум
5 115 886, все 10 прогонов в плюсе.

Эффекты в мок-среде выдуманы организаторами, поэтому эти цифры показывают, что
механика работает и результат устойчив, а не каким будет балл на судействе.

## Как запустить

```bash
pip install -r requirements.txt
python local_eval.py              # один прогон с отчётом
python local_eval.py --runs 10    # 10 прогонов с разными seed
python make_submission.py         # собрать submission.csv
```

Агент не использует случайность, поэтому `submission.csv` при повторном запуске
получается один и тот же.

## Чего пока нет

- LLM в контуре решений не используется.
- Сегменты по трафику и звонкам (`data_segment`, `call_segment`) не
  используются, аудитория делится только по тарифу и ARPU.
- Все пилоты идут через SMS. Эффект других каналов пересчитываем по их
  коэффициентам, а не проверяем отдельно.
- Шум пилота задан константой (`PILOT_NOISE = 0.8`), а не оценивается по данным.
